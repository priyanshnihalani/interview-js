> **Module 1: JS Runtime Internals, Mental Model & Output Tracing**

> **Estimated Study Time:** 2.5 Hours  

---

## 1. Core Mental Model: Execution Context (EC)

In JavaScript, code is never executed directly in isolation. Every piece of JavaScript code runs inside an **Execution Context (EC)**—an abstract environment that holds everything required to evaluate that code (variables, functions, scope chain, and `this`).

### The Types of Execution Contexts:
1. **Global Execution Context (GEC):**
   - Created by default when the JS engine first loads and parses the script.
   - Exactly **one** GEC exists per JavaScript thread.
   - Sets up the global object (`window` in browsers, `global` in Node.js) and binds global `this`.
2. **Function Execution Context (FEC):**
   - Created dynamically **every single time a function is invoked** (`fn()`), **never** when the function is defined/declared.
   - Each invocation receives a distinct, isolated FEC with its own arguments, local variables, and outer lexical reference.
3. **Eval Execution Context:**
   - Created when code runs inside `eval(...)` (rarely used in production; avoided due to performance and security hazards).

---

## 2. The Two-Phase Lifecycle of an Execution Context

Whenever an Execution Context is instantiated (GEC or FEC), the JavaScript engine evaluates it in **two distinct phases**:

```
+-------------------------------------------------------------------------+
|                       Execution Context Lifecycle                       |
+-------------------------------------------------------------------------+
|  Phase 1: Creation Phase (Compile / Memory Allocation)                  |
|  - Creates Lexical Environment & Variable Environment                   |
|  - Hoisting:                                                            |
|      * Function Declarations: Stored with full function object body     |
|      * `var` variables: Allocated in memory and initialized to undefined|
|      * `let` / `const` variables: Allocated in memory uninitialized     |
|        (Temporal Dead Zone - TDZ)                                       |
|  - Binds the `this` keyword value                                       |
|  - Establishes `[[OuterEnv]]` reference (pointer to parent lexical scope|
|    where the function was written)                                      |
+-------------------------------------------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
|  Phase 2: Execution Phase (Code Evaluation)                             |
|  - Runs code line-by-line from top to bottom                            |
|  - Evaluates expressions and assigns real values to variables           |
|  - Encounters function invocations -> pushes a new FEC to Call Stack   |
|  - Encounters `return` or end of function -> pops current FEC           |
+-------------------------------------------------------------------------+
```

---

## 3. The Call Stack Mechanics

The **Call Stack** is a LIFO (Last-In, First-Out) data structure that manages the order of Execution Contexts.

1. **Script Start:** The GEC is pushed onto the stack.
2. **Function Call:** A new FEC is created and pushed on top of the stack.
3. **Nested Calls:** Each nested call adds another frame on top.
4. **Return:** When a function reaches `return` (or completes), its FEC is **popped off** the stack.
5. **Script End:** When the script finishes, the GEC is popped off.

```
Example:
function a() { b(); }
function b() { c(); }
function c() { console.trace(); }
a();

Call Stack Progression:
[Push GEC] -> [Push FEC(a)] -> [Push FEC(b)] -> [Push FEC(c)]
                                                      |
                                             c finishes: Pop FEC(c)
                                                      |
                                             b finishes: Pop FEC(b)
                                                      |
                                             a finishes: Pop FEC(a)
```

## 4. Interview Trap 1: Identifier Collision in Creation Phase

A favorite interview question tests how the engine resolves collisions between **Function Declarations** and **`var` Declarations** sharing the same name in the same scope.

### The Code:
```javascript
console.log("1:", typeof foo);

var foo = "Hello";

function foo() {
  return "World";
}

console.log("2:", typeof foo);

function bar() {
  console.log("3:", typeof baz);
  return;
  function baz() {}
}

bar();
console.log("4:", typeof baz);
```

### The Output:
```text
1: "function"
2: "string"
3: "function"
4: "undefined"
```

### The Engine Mechanics:
1. **Creation Phase Priority Rule:**
   - **Function Declarations hoist first** and are assigned their function reference.
   - When the engine scans `var foo`, it detects `foo` is already declared as a function. The engine **skips** initializing it to `undefined`—the function declaration takes precedence during Creation Phase.
   - Therefore, at line 1, before any assignment runs, `foo` is the function.
2. **Execution Phase Assignment:**
   - `var foo = "Hello";` is executed as an assignment: `foo = "Hello"`.
   - The primitive string overwrites the function in memory. Line 2 logs `"string"`.
   - `function foo() {}` was already handled in the Creation Phase, so it is a no-op during execution.
3. **Hoisting Ignores `return`:**
   - Inside `bar()`, `function baz() {}` is hoisted into `bar`'s local FEC during its Creation Phase, **even though it is physically placed after `return`**.
   - Line 3 logs `"function"`.
4. **Scope Boundaries:**
   - `baz` was declared inside `bar`'s local FEC. When `bar()` finishes, its FEC is destroyed.
   - In global scope, `baz` was never declared. In JavaScript, `typeof <undeclaredVariable>` safely returns `"undefined"` without throwing a `ReferenceError`.

## 5. Interview Trap 2: Stack Overflows & Unbounded Recursion

A classic problem posed in senior interviews:
> *"A recursive function processing 100,000 nodes crashes with `RangeError: Maximum call stack size exceeded`. How do you solve this without switching to an iterative `while` loop?"*

Every JavaScript engine imposes a hard limit on call stack depth (typically ~10,000 frames in V8).

### Solution Approach A: Asynchronous Chunking (`queueMicrotask` / `setTimeout`)

```javascript
function processNodeAsync(node, callback) {
  if (!node) return callback();

  // Do work on node...
  
  // Schedule next iteration via microtask or macrotask
  queueMicrotask(() => {
    processNodeAsync(node.next, callback);
  });
}
```

#### Why it prevents Call Stack Overflow:
- When `queueMicrotask(...)` is called, the current function returns immediately and its FEC is **popped off the Call Stack**.
- When the microtask queue executes the callback on the next tick, the call stack depth is **1**. It never grows beyond 1.

#### ⚠️ Critical Nuance (Event Loop Starvation):
- The browser / Node.js will **never** render UI or execute macrotasks (`setTimeout`, I/O) until the microtask queue is completely drained.
- Running 100,000 microtasks consecutively will **block the main thread** and freeze the UI.
- **Fix:** Use macrotask chunking (`setTimeout(..., 0)`) or `scheduler.yield()` / `requestIdleCallback` to allow the engine to breathe and paint between chunks.

---

### Solution Approach B: The Pure Synchronous Solution — **The Trampoline Pattern**

If the interviewer specifies:
> *"The solution MUST remain completely synchronous. No promises, no event loop, no async queues allowed."*

The answer is **Trampolining**.

A trampoline wraps a recursive algorithm such that instead of calling itself directly (which adds a stack frame), the recursive function returns a **thunk** (a zero-argument function wrapping the next step). The trampoline runner loops over the thunk until a non-function value is returned.

```javascript
/**
 * Generic Trampoline Runner
 * Keeps the call stack depth strictly at 1.
 */
function trampoline(fn) {
  return function (...args) {
    let result = fn(...args);
    // While the result is a function (thunk), execute it iteratively
    while (typeof result === "function") {
      result = result();
    }
    return result;
  };
}

/**
 * Trampolined recursive accumulator
 * Returns a thunk instead of invoking directly.
 */
function sumList(node, acc = 0) {
  if (!node) return acc;
  // Return a closure thunk: current frame exits before next step begins!
  return () => sumList(node.next, acc + node.val);
}

// Usage:
const safeSum = trampoline(sumList);
// Can process 1,000,000+ nodes synchronously with 0 stack overflow!
```

## 📌 Summary Cheatsheet for Whiteboard & Verbal Interviews

| Concept | Golden Rule / Mental Model |
| :--- | :--- |
| **GEC vs FEC** | GEC is created once on start; FEC is created on every invocation. |
| **Two Phases** | Phase 1: Allocate memory & hoist. Phase 2: Execute code & assign values. |
| **Functions vs `var`** | Function declarations hoist first and take priority over `var` in Creation Phase. |
| **Dead Code Hoisting** | Hoisting happens in Phase 1 regardless of `return` or unreachable blocks. |
| **`typeof` on Undeclared** | Returns `"undefined"`, does not throw `ReferenceError`. |
| **Stack Overflow Defense** | 1. Async scheduling (`queueMicrotask` / `setTimeout`) pops frame before next tick.<br>2. Trampoline pattern converts recursion into an iterative thunk loop at stack depth 1. |
